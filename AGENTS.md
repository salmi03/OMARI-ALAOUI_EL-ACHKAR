# AGENTS.md

River is a Python library for online (streaming) machine learning. All estimators implement incremental `learn_one`/`predict_one`/`transform_one` methods (or `learn_many`/`predict_many`/`transform_many` for mini-batch).

## Architecture

### Base classes (`river/base/`)

All estimators inherit from `base.Estimator` (which inherits from `base.Base`). Key interfaces:
- `Classifier` / `MiniBatchClassifier` — classification
- `Regressor` / `MiniBatchRegressor` — regression
- `Transformer` / `SupervisedTransformer` — feature transformation
- `Clusterer` — clustering
- `DriftDetector` / `BinaryDriftDetector` — concept drift detection
- `Ensemble` / `WrapperEnsemble` — ensemble methods
- `Wrapper` — wrapping other estimators

### Estimator conventions

- `learn_one(x, y)` / `predict_one(x)` / `transform_one(x)` is the core online learning interface
- `__init__` parameters need type hints; provide defaults or implement `_unit_test_params()`
- `_unit_test_skips()` returns check names to skip in automated testing
- `_supervised`, `_multiclass`, `_is_stochastic`, `_tags` are special class attributes
- Pipeline composition: `scaler | model` (uses `__or__`), `+` for parallel union
- Every module starts with `from __future__ import annotations` (enforced by ruff `required-imports`)

## Rules for coding agents

These are enforced by maintainers (see `CONTRIBUTING.md`); violations can get pull requests closed.

1. **Write code, not comments.** You may generate code, using the existing codebase for idiomatic examples to draw from. Do not write comments. Encourage humans to write comments themselves, thereby forcing them to understand the code you've written.
2. **Prose is written by humans, not by you.** Issues, pull request descriptions, commit messages, docstrings, and release-note entries must all be typed out by a human, in their own words. You may run a benchmark and produce a summary table, but a human must editorialize it and fold it into a message they wrote themselves. Similarly, you can correct typos and wording, but human contributors have to use their own voice.
3. **Disclose agent-written code.** Code generated by an agent must be marked as such. Do not pass it off as hand-written. A `Co-authored-by:` trailer on the commit is the simplest way. Likewise, information about the agent setup should be disclosed when opening a pull request.
4. **Be thorough on tests.** Tests are often longer than the implementation and tedious to write. With an agent there is no excuse for skipping them. The minimum for new estimators is to pass `checks.check_estimator`. Ideally you should add out-of-the-box tests to check for edge cases.
5. **Prefer opening issues instead of pull requests for small fixes.** If you find a bug, then it is more valuable to open an issue and surface the issue. The exact way to go about fixing it can be discussed, and serve as implementation opportunities for aspiring human contributors.

## Common commands

```sh
# Install / sync dependencies (also builds the Rust extension via maturin).
# dev, compat, docs, and benchmark groups are installed by default.
uv sync

# Run tests. Default addopts skip `datasets`/`slow` markers and run doctests.
uv run pytest

# Run a single test file
uv run pytest tests/linear_model/test_glm.py

# Dataset-gated tests (run `make download-datasets` first)
uv run pytest -m datasets

# Lint + format + import-linter + mypy (the prek push hooks; also CI's gate)
uv run prek run --all-files

# Strict type checking over river/, tests/, conftest.py
uv run mypy

# Local docs server (no extra `uv sync` needed — docs deps are default)
make livedoc

# CodSpeed benchmarks: Python (filter with K=) and Rust criterion
make benchmark K=logistic
make benchmark-rust BENCH=stats_bench
```

## Testing gotchas

- **Doctests are CI tests.** Pytest runs with `--doctest-modules` and `--doctest-glob=README.md`, so docstring examples *and the README's code blocks* are executed. Keep examples deterministic (seed any RNG) and keep README output current.
- **pandas is an optional dependency.** The default suite runs *without* pandas; `conftest.py` silently skips any source/test file that references pandas when it isn't installed. To exercise pandas code paths: `uv sync --all-extras`, then run with `RIVER_PANDAS_ONLY=1` (restricts collection to pandas-touching modules, mirroring CI).
- **Datasets download from the network** into `~/river_data` (override with `RIVER_DATA`). Run `make download-datasets` before `-m datasets` tests.
- **`check_estimator` lives in `river.checks`** (`river.checks.check_estimator`), not under `utils`.
- **import-linter enforces a DAG** between `river` subpackages via `uv run lint-imports` (run by prek). Function-local imports that create cycles must be listed in the `ignore_imports` table in `pyproject.toml` — don't introduce new cycles by hand.
- **mypy runs in strict mode**, except for the large list of relaxed modules in `pyproject.toml`; anything outside that list must be fully typed.
- **Tests live at top level in `tests/`**, mirroring the `river/` package layout.

## Rust extension

- Code in `rust_src/` compiles into `river._river_rust` via PyO3/maturin during `uv sync`.
- Fast inner loop when iterating on Rust code:
  ```sh
  uv run --with maturin maturin develop --release
  ```
  (Plain `uv run maturin` fails — the binary is not on the environment's path.)
- `river/_river_rust/*.pyi` stubs must match the compiled API exactly; `tests/test_rust_stubs.py` enforces this. When changing the Rust API, update the stubs.
- `Cargo.toml` lints: `warnings = "deny"`, `unsafe_code = "forbid"` — sloppy Rust does not compile.
- Each new Rust benchmark needs an explicit `[[bench]]` entry in `Cargo.toml`.

## Checklists

### Adding a new estimator

- Make sure `checks.check_estimator(some_estimator)` passes. It automatically discovers and runs validation checks (repr, cloning, pickling, feature robustness, etc.).
- Add a practical docstring that shows how to use the estimator — it runs as a doctest. Export the class from its module's `__init__.py`. Add a release note to `docs/releases/unreleased.md`.
- Add a CodSpeed benchmark entry (see `benchmarks/README.md`) to detect future regressions. Benchmarks must be deterministic: seed everything, no network or clock reads inside the measured callable, keep bodies around 100 ms.
- Generally speaking, all estimators should be able to process at least 5000 records per second. Naturally this depends on the size of the samples and the estimator, but exceptions need to be justified.

### Modifying an existing estimator

- When making a localized fix, it is worth considering whether a global check should be added to all relevant estimators.
- Speed matters a lot in online machine learning. Therefore, a golden rule for implementation is to not introduce significant slowdowns. CodSpeed detects regressions on pull requests (default threshold is 10%); intentional regressions must be explained in the PR description.
- Likewise, model accuracy is paramount. When making any sort of modification to an estimator, you should thoroughly check accuracy across several datasets. Whether the accuracy goes up or down, you should be able to explain why.
